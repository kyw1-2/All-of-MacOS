# 메인 화면 응답성 개선 — 2026-11-13

기준: 설치된 3.4.41 / `9ce9e666b026aaf99f088d1f31e0860b5fc61e81`.
이전 최적화가 설치되지 않아 생긴 문제는 아니다. 이번 변경은 소스 검증과 로컬 커밋까지이며 릴리즈 빌드·설치는 포함하지 않는다.

## 확인한 병목

Workspace를 열고 설치 앱의 스택을 12초와 20초 동안 수집했다.
첫 샘플에서 메인 스레드 6,944개 관측 중 1,078개가
`AudioOutputService.volumeProperty`에 있었고, 그 아래에는 CoreAudio의
동기 IPC 대기가 보였다. 호출자는 매번 기본 소프트웨어 음량을 확인하는
`AppAudioEngine.syncActiveProcesses`였다.

두 번째 샘플에서는 닫힌 Mission Control의 주기적 잠금 상태 조회,
`SystemStatusMonitor.sample`의 디스크 조회와 볼륨 열거,
`AOMHomeView.refreshStatus`의 앱/단축키 조회,
`AOMHomeView.todayCard`의 렌더 경로도 확인했다.
샘플 수는 CPU 점유율이나 개별 호출의 정확한 소요 시간이 아니다.

코드상 대시보드는 GestureStatistics와 오디오 모델 전체를 직접 관찰하고 있었다.
따라서 동작이 실행되지 않은 입력 감지나 재생 상태만 바뀌어도 페이지가
갱신 대상이 됐다. 주간 통계는 렌더마다 모든 기록을 달력 날짜별로 다시 묶었다.

## 변경

- **오디오 기본 음량**: 저장된 소프트웨어 음량이 1이면 결과는 장치와 관계없이 1이다.
  이 경로에서는 장치 목록·전송 방식·음량 지원 여부 조회를 생략한다.
  실제 감쇠가 설정된 경우 기존 지원 여부 검사는 유지한다.
  여러 세션이 같은 출력을 사용하면 한 번의 동기화 안에서 음량 결과를 공유한다.
- **Mission Control**: 닫힌 상태의 잠금 조회를 기존 백그라운드 탐색 큐에서 실행한다.
  실제 오버레이를 표시하기 직전과 사용자 동작의 잠금 검사는 유지한다.
- **시스템 상태**: CPU·메모리·디스크·배터리·네트워크·볼륨 조회를 utility 작업으로 옮긴다.
  한 번에 한 조회만 허용하며, 화면이 닫히거나 다시 열렸을 때 이전 결과를 폐기한다.
  CPU의 이전 표본과 느린 항목의 5회 간격 갱신을 보존한다.
- **Workspace 상태**: 다른 앱의 단축키와 오디오 출력 조회를 백그라운드로 옮긴다.
  Workspace와 This Mac 카드의 폴링은 실제 호스트 창의 가시성을 따른다.
- **관찰 범위**: 입력 감지 전체 대신 실행된 동작 기록을 관찰한다.
  오디오는 화면에 쓰이는 켜짐·EQ·사용자 설정 앱 수가 바뀔 때만 페이지를 갱신한다.
  최근 동작은 제한된 기록 버퍼 안의 최근 실행 5개를 사용한다. 미실행 감지 64개가
  뒤에 쌓였다는 이유만으로 최근 실행이 화면에서 사라지던 현상도 없어진다.
- **통계와 차트**: 기록·날짜·달력이 같으면 주간 집계를 재사용한다.
  자정·시간대·달력 변경 및 기록 수정 시 갱신하며, 동일 데이터의 차트는 재구성하지 않는다.

## 검증

`bash scripts/run-tests.sh -j 2`: **69개 통과, 실패 0**.
새 테스트 7개는 다음을 확인했다.

- 기본값·잘못된 음량에서 하드웨어 조회 0회, 실제 감쇠·음소거·미지원 장치의 기존 결과 유지.
- 입력 감지 500회: 원본 모델의 변경 알림 1,000회에 대해 대시보드 projection 변경 알림 0회.
  실제 실행, 버퍼에서의 실행 기록 만료, 초기화는 정상 반영.
- 같은 오디오 요약 200회에 대해 대시보드 변경 알림 0회, 표시값 변경은 반영.
- 주간 집계의 기록 변경·자정·시간대 무효화와 집계 결과.
- 시스템 조회를 의도적으로 대기시켜도 MainActor가 진행하고, 중복 요청이 겹치지 않으며,
  중단 이후 도착한 결과가 화면에 발행되지 않음.
- 시스템의 느린 항목 갱신 간격과 CPU 표본 차이 계산.

앱·테스트 타깃의 컴파일을 통과했다. 기존 코드의 동시성 관련 경고는 남아 있으나,
이번에 추가한 상태 조회의 함수 변환 경고는 명시적인 Sendable 클로저로 정리했다.

## 부분 벤치마크

실제 `WorkspaceWeekCache` 소스를 추출한 release 최적화 실행에서, 동작 2,048개,
캡처 50개, 복사 400개인 합성 데이터를 사용했다. 같은 날짜·기록을 사용하는
재계산을 300회씩 4라운드 교차 실행했다. 날짜 배열 복사도 새 경로에 포함했다.

- 기존 집계 평균: **2.638 ms/회**.
- 캐시 재사용 평균: **0.0159 ms/회**.
- 모든 날짜별 결과 일치.

이는 해당 집계의 결과이며 전체 앱 속도·FPS 개선 배율이 아니다.

## 한계와 후속 확인

원래 Capture 화면을 Workspace로 전환해 관측한 뒤 Capture로 복원했다.
CUA 스크롤 동작에서 `elementHasNoFrame`/`noWindowsAvailable` 오류가 발생해
일정한 스크롤 입력에 따른 전후 FPS 비교는 성립하지 않았다. 해당 실패를
성능 개선의 증거로 사용하지 않았다. 반복 오류에 대한 로컬 reflection에서도
검증된 복구 전략이 없어 규칙이나 스킬 변경을 채택하지 않았다.

새 버전 설치 후 실제 스크롤·탭 전환·오디오 출력·잠금/해제·창 숨김/재개를
확인해야 한다. 현재 설치 앱을 교체하지 않았으므로 버벅임이 완전히 사라졌다고
주장하지 않는다. 계측 시 시스템 전체 부하도 높아 앱 변경만으로 모든 지연을
설명할 수는 없다.

백그라운드 앱 목록 조회의 스레드 안전성은 SDK 헤더와
[Apple NSWorkspace.runningApplications 문서](https://developer.apple.com/documentation/appkit/nsworkspace/runningapplications)에서 확인했다.
